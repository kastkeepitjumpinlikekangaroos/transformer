SQL data pipelines

Your whole data pipeline in one jar and one folder of SQL.

transformer runs DBT-style pipelines (staging, marts, data-quality tests) on a single machine with its own parallel SQL engine. You don't need a warehouse, a cluster, or a Python environment. Install Java and run one jar against a folder of SQL files.

01 / one dependency

Nothing to deploy but a jar

The SQL parser, planner, and executor ship inside transformer, so there's no Spark, database, or warehouse behind it. Reading and writing CSV and Parquet is built in. If a machine has Java 21, it can run your pipeline: a laptop, a CI runner, an Airflow worker, or a container.

02 / fast iteration

Edit, run, look, in seconds

A pipeline is plain files on disk. Change a main.sql, rerun, and the 15-table jaffle-shop example finishes in about two seconds. The desktop GUI draws the DAG, shows live task status, previews every output, and has a SQL console for poking at results, in an editor that highlights SQL and takes vim's keys.

03 / agent first

Built for coding agents

Every part of a project has a fixed place and a fixed shape, and the CLI reports through exit codes and JSON run records. An agent such as Claude Code can scaffold a pipeline, run it, read what failed, and fix it without any UI or cloud console.

How it works

A pipeline is a folder

Each input is a directory with a small JSON config. Each table is a directory with a main.sql. A data-quality test is a SQL file in that table's validations/ folder, and it passes when it returns no rows.

transformer reads which tables each query references, builds the dependency graph from that, and runs independent branches in parallel. You never declare the order.

  • Joins, aggregates, window functions, CTEs, UNION, CASE, and casts, with strict typing that refuses an ambiguous query instead of guessing
  • Reads and writes CSV and Parquet, using Parquet row-group pruning and parallel scans
  • Paths and SQL accept time variables like {{ today }}, so each scheduled run writes its own partition
  • Every run leaves a job.json and a per-task _run.json with status, row counts, timings, and samples of the rows that failed a validation
jaffle_shop/job/
  inputs/
    raw_orders/
      config.json        {"path": "data/raw_orders.csv"}
  tables/
    stg_orders/
      main.sql
    orders/
      main.sql
      output.json        {"format": "parquet"}
      validations/
        order_id_unique.sql
        order_total_balances.sql

tables/orders/validations/order_total_balances.sql

-- Passes when no rows come back.
SELECT order_id, subtotal_cents, tax_paid_cents, order_total_cents
FROM orders
WHERE subtotal_cents + tax_paid_cents <> order_total_cents

Agent first

Hand the pipeline to your agent

Coding agents are good at editing structured text and running commands, and transformer projects are only that. There's no service to log into, no notebook state, and no hidden metadata. The agent's whole loop happens on the local machine:

  • Scaffold. Make a directory per table and write the SQL. The layout is the same in every project, so an agent can copy it from one example.
  • Run. transformer run <jobDir> exits 0 only when every task and validation passes.
  • Diagnose. Each failed task prints its reason, and job.json names failing validations with row counts and points to a CSV of sample bad rows.
  • Verify. Data-quality checks are SQL files the agent writes next to the table it's changing.

A prompt like this is enough

Add a weekly_revenue table to the jaffle shop job
that sums order_total per location per week, with
validations that location_id is never null and the
totals match orders. Run it until everything passes.

Run it anywhere

Same project, from the CLI, the GUI, or a scheduler

The same jar runs headless from the command line or opens the desktop GUI. In Airflow, cron, or CI, a run is one shell command with a nonzero exit code on failure. Pass the scheduler's logical date as the execution time and every {{ today }} in your SQL and paths resolves to that date, so reruns and backfills land in the right partition.

Then open the data viewer, a jar of its own, on the folder your jobs write to. It shows every job's tables, draws their lineage within each job and across jobs (one job's input read from another's output), opens a sample of any table on a double-click, and runs SQL over all of them in the same editor.

Set up the example project

Desktop GUI

$ java -jar transformer.jar gui examples/jaffle_shop/job

Data viewer

$ java -jar transformer_viewer.jar /data/runs

Airflow

BashOperator(

    bash_command=(

        "--execution-time {{ ts }}"
    ),
)
